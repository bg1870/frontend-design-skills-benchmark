It should be loaded whenever the task requires choices about layout, typography, imagery, styling, or visible interaction states, even if the brief does not explicitly request visual quality. It should not be loaded for backend-only work, invisible logic changes, CLI tools, data processing, or prose-only deliverables with no browser interface.

# Beautiful frontend

## Decide before composing
- Work from the brief without asking questions. Treat explicit requirements, supplied references, and the host site's established design as constraints; use the rules below to resolve unspecified choices, not override them.
- For an extension, inspect the surrounding interface and its styles first. Match its content width, type roles, spacing, control geometry, and interaction conventions. Put new character into the requested surface, not an unsolicited redesign of the shell.
- Before markup, privately name the audience, their next action, and the content they must notice first. Write the actual headline or screen title, primary action label, and representative content now; do not design empty boxes and fill them later.
- Consider two compositions that differ structurally, not just chromatically: a product specimen beside an argument versus a full-width demonstration; a queue-first workspace versus a map-first workspace. Choose the one that exposes the user's task or the offer's evidence sooner. Implement only that one.
- Commit to three observable decisions: a spatial relationship, a typographic hierarchy, and a material/color treatment. Replace adjectives with consequences: “precise” might mean aligned units, compact rows, and hairline rules; “tactile” might mean close-cropped material photography and broad, quiet margins. Do not translate every brief into the same warm-white serif page or dark neon console.
- Derive one recurring detail from the subject: route lines for transit, index numbering for an archive, cut-paper edges for a collage exhibition. Use it in two or three meaningful places. In an existing product, reuse its signature instead of inventing a competing one. Distinction can live in alignment and type; it need not be ornament.

## Compose the content, not a component catalog
- Make the first viewport perform the task. A marketing page needs a specific offer, visible evidence, and a next step; a dashboard needs scope, current condition, and actionable records; a prototype needs the core interaction in a usable state. Do not put a promotional hero above a working interface by habit.
- Give that viewport one dominant object: a headline, photograph, product demonstration, map, or working data region. Lower the size, saturation, or contrast of competing regions until the intended reading order is unmistakable. A full-width table can be the focal object; not every page needs giant type.
- Build the defining object before secondary sections. A scheduling product needs a credible schedule, a store needs product presentation, and an analytics tool needs legible data. Do not substitute a floating cluster of generic cards for the thing being sold or used.
- Establish a shared alignment grid. Headings, paragraphs, media edges, and section rules should land on common axes. For unequal roles, try a 7:5 or 8:4 split instead of automatic equal columns; use equal columns when the content really is a comparison. Permit a deliberate breakout, not accumulated alignment accidents.
- Size the container for the work: roughly 65–75rem for a reading-led page, 80–90rem for a media-led page, and available width for a dense workspace. Keep prose narrow inside wider layouts. Inherit host widths when extending a site.
- Space by relationship. Start with a small token set such as 4, 8, 12, 16, 24, 32, 48, 64, 96px; use an internal gap at most half the gap separating independent groups. Dense tools should use the lower range, not marketing-page padding around every row.
- A card must represent an independently actionable item, a bounded comparison, or a distinct surface. Use rows, separators, bands, and whitespace for other grouping. Remove card-inside-card framing unless the inner surface really has separate behavior.
- Give each marketing section a different reader question to answer. Change composition when the argument changes: demonstration, comparison, process, evidence. Do not repeat the same three-card grid with new icons, or alternate backgrounds merely to manufacture sections.
- Preserve repetition where it aids comparison: identical pricing attributes, table rows, and repeated controls should align. Put asymmetry in page composition, not arbitrary offsets between equivalent items.
- Do not fill spare space with invented KPIs, badges, logo clouds, or floating widgets. If a region is weak, enlarge the relevant evidence, improve its crop, shorten the layout, or delete the region.

## Make typography do structural work
- Choose type for the content's demands: a readable text face for long arguments, distinct numerals for a data tool, an expressive display face for a short identity-led statement. A familiar system face is valid when layout carries the identity; an unusual font does not rescue a generic layout.
- For new work, limit typography to two families and three useful weights. Define roles for display/title, section heading, body, label, and numeric data rather than assigning sizes independently to components. Use available fonts and a metric-compatible fallback; do not depend on a font that may never load.
- Make size contrast intentional. On a marketing desktop, a focal heading can be 2.5–4 times body size; in a tool, a screen title is usually only 1.4–2 times body size. Keep public-page body text around 16–18px; use 13–15px for dense supporting data rather than shrinking the whole interface.
- Set body leading around 1.45–1.65 and large-heading leading around 1.0–1.15, adjusting for the font and script. Test accented capitals and descenders for clipping. Use slightly tighter tracking on large display text only; do not compress body copy or letterspace every label.
- Constrain prose to roughly 45–70 characters per line and leads to 30–45. Tune heading width and fluid size before inserting manual line breaks. If a deliberate phrase break is necessary, remove it at widths where it produces a one-word line or overflow.
- Use tabular numerals and right alignment for comparable numeric columns. Attach units and date context; distinguish the value from its label by size or weight rather than coloring every metric.
- Write in the domain's nouns and verbs. Replace “Unlock powerful insights” with the actual benefit or task; replace “Get started” with a destination-specific action when known. Headings must say what the section contains, not just “Elevate,” “Discover,” or “Why us.”
- For fictional prototypes, use plausible, internally consistent names, dates, prices, and records, including long labels and uneven values. Mark demo data where it could be mistaken for fact. Do not invent real endorsements, customer logos, awards, or performance claims.

## Color, surfaces, and imagery
- Define color roles before styling components: canvas, surface, primary ink, secondary ink, rule, action accent, and semantic statuses. Choose the neutral temperature and accent from the subject or host brand. Do not select purple/blue gradients, beige/orange, or near-black/lime merely because they are familiar defaults.
- Reserve the strongest control contrast for the primary action within each decision group. Secondary actions should recede without becoming illegible. Keep decorative brand colors separate from error, warning, and success meanings.
- Choose one dominant surface treatment. Flat fields and rules, soft elevated surfaces, or image-led planes can each work; do not stack glass blur, glow, grain, gradients, and heavy shadows. Keep an effect only if it reinforces the chosen material treatment or explains a layer/state.
- Use a small radius vocabulary tied to roles, not one enormous radius everywhere. Pills suit chips and compact toggles; text sections do not need pill-shaped containers. Shadows should communicate elevation or separation, not outline every object twice with both border and shadow.
- If imagery carries the design, give it enough area to reveal its subject. Choose an intentional crop and focal position, preserve intrinsic aspect ratio, and check the mobile crop separately. Avoid putting a tiny illustration inside a vast empty hero frame.
- Use relevant available assets, not arbitrary stock imagery that happens to match the palette. When suitable imagery is unavailable, change to an honest type-, product-, or diagram-led composition. Never leave broken images, empty media placeholders, or a crude vector pretending to be a photograph.
- Product previews must contain readable, coherent UI: meaningful labels, consistent sample values, and a demonstrated operation. Charts need units, scales or direct labels, and data that supports the surrounding claim; decorative squiggles are not evidence.
- Use icons to speed recognition or clarify an action, not to decorate every heading. Keep one stroke/fill family and optical size; pair unfamiliar icons with labels. Do not use emoji as replacement interface assets unless the product's visual language calls for them.
- Maintain at least 4.5:1 contrast for ordinary text, 3:1 for large text, and 3:1 for essential control boundaries and focus indicators. Muted text must remain readable on its actual surface. Give status a word, symbol, or pattern in addition to hue.

## Make the design survive use
- Reuse the project's stack and primitives, but explicitly style their type, spacing, and states; untouched library defaults are not an art direction. Put repeated values into shared tokens and repeated visual structures into shared components so later sections cannot drift.
- Every visible control needs a real result. Links navigate to a valid destination; tabs change panels; filters alter records; plan selectors update the relevant price and selection. In a local prototype, implement truthful local behavior instead of wiring every action to the same toast or pretending a remote operation succeeded.
- Design default, hover, keyboard-focus, selected, disabled, loading, empty, and error states where applicable. Keep borders and dimensions stable across states. Empty results should explain what happened and offer the relevant recovery action, not leave a blank frame.
- Use native buttons, links, and form controls with associated labels. Keep visible keyboard focus, such as a 2px outline with 3px offset. Make icon-only controls accessible by name; dialogs must accept keyboard dismissal and return focus to their trigger.
- On narrow screens, reorder by task importance rather than simply stacking desktop columns. Keep the main action and relevant evidence early; turn sidebars into compact navigation, not a screenful of links above the content. Use about 16–24px outer gutters rather than retaining desktop margins.
- Let content determine breakpoints: split layouts collapse before either side becomes unreadable. Use fluid display type and flexible tracks; avoid fixed hero heights that clip wrapped copy. Keep a dense table's horizontal scrolling inside its region instead of hiding page overflow or shrinking all text.
- Give touch actions approximately 44×44px hit areas, enlarging the invisible target if the visible icon is smaller. Ensure sticky headers and action bars do not cover anchors, focused controls, or the last content row.
- Use motion to explain a state change: roughly 120–220ms for feedback, slightly longer for a panel entering. Animate opacity and transforms rather than layout where possible. Honor reduced motion; do not gate readable content behind an entrance animation or add continuous floating motion for atmosphere.

## Inspect and revise the artifact
- If rendering is available, inspect the actual page after fonts and images settle at a wide viewport (about 1440×900) and a narrow one (about 390×844), then check an intermediate width. Use existing capabilities; this skill requires no extra tools. If you cannot render, audit the layout constraints and state paths without claiming visual verification.
- First inspect large masses: what wins attention, where the grid breaks, whether empty space separates ideas or merely delays content. If everything looks equally important, change scale and layout before adjusting colors.
- Then inspect actual text wraps, image crops, baseline alignment, clipped content, faint labels, and repeated padding. Fix the three most visible defects in the rendered result, starting with composition, then type and imagery, then small decoration. Do not stop at “it compiles.”
- Exercise the primary journey and keyboard navigation. Check a long title, missing image, zero results, selected state, and validation error where relevant. Compare repeated controls and lower-page sections with the first viewport; they must use the same visual rules.
- Run a substitution test: if changing only the logo and headline would let this pass for an unrelated product, replace a generic major region with domain-specific content or composition. A hue swap, louder gradient, or novelty font does not pass this test. For host-site extensions, judge specificity through the task and data rather than forcing new branding.
- Remove any remaining section, border, icon, or flourish that duplicates a job already done. When time is short, ship fewer fully resolved regions and a working primary path rather than a long scaffold of placeholder sections.
