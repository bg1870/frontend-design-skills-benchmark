# Review: `fixtures/site`

## Overall score: **43/100 — significant accessibility and mobile usability problems**

The page is visually coherent and the content hierarchy is understandable, but several core interactions are inaccessible, most body copy fails contrast requirements, and the mobile layout is likely to overflow. Fix accessibility fundamentals before visual polish.

1. Restore visible keyboard focus.
2. Make integration rows real, named links or buttons.

## Findings

### 1. No keyboard focus indicator anywhere

**Severity: Critical**

`fixtures/site/styles.css:29` declares:

```css
:focus { outline: none; }
```

There is no replacement `:focus-visible` style. Keyboard users cannot see which navigation link, button, or form field is active.

**Rule:** WCAG 2.4.7 Focus Visible and WCAG 2.4.11 Focus Appearance. Interactive elements must have a visible focus indicator.

**Fix:** Remove the blanket reset or replace it with a high-contrast `:focus-visible` treatment for links, buttons, and inputs.

---

### 2. Integration rows are mouse-only controls

**Severity: Critical**

Each row uses `onclick` on a non-focusable `<li>`:

- `fixtures/site/index.html:43`
- `fixtures/site/index.html:47`
- `fixtures/site/index.html:51`
- `fixtures/site/index.html:55`
- `fixtures/site/index.html:59`

The row cannot be reached or activated using the keyboard. The nested arrow buttons at lines 45, 49, 53, 57, and 61 have no handler of their own and no accessible name.

**Rules:**

- WCAG 2.1.1 Keyboard: all functionality must be keyboard operable.
- WCAG 4.1.2 Name, Role, Value: controls need an accessible name and correct role.
- Native interactive semantics are required rather than click behavior attached to static list items.

**Fix:** Use one real `<a href="#signup">` or `<button>` for each entire row. Treat the arrow SVG as decorative rather than as a second unnamed control.

---

### 3. The signup field has no accessible label

**Severity: Critical**

`fixtures/site/index.html:70` relies only on:

```html
placeholder="Work email"
```

A placeholder is not a label; it disappears after entry and may not reliably identify the field to assistive technology.

**Rules:**

- WCAG 1.3.1 Info and Relationships.
- WCAG 3.3.2 Labels or Instructions.
- WCAG 4.1.2 Name, Role, Value.

**Fix:** Add a persistent `<label for="…">`, an input `id`, and associate them explicitly.

---

### 4. Most supporting text fails minimum contrast

**Severity: High**

`fixtures/site/styles.css:4,25` uses `#9aa3ad` for paragraphs against `#fbfaf7`, producing approximately **2.45:1** contrast. Against white cards it is approximately **2.56:1**.

The same color is used for:

- Navigation links: `styles.css:40`
- Icon controls: `styles.css:70`
- Body paragraphs: `styles.css:25`
- Footer copy: `styles.css:90`

**Rule:** WCAG 1.4.3 Contrast (Minimum) requires **4.5:1** for normal text. These texts are 13–16px, so the large-text exception does not apply.

The placeholder also inherits browser styling without an explicit compliant color; its effective contrast is therefore uncontrolled.

**Fix:** Replace `--muted` with a substantially darker color that reaches at least 4.5:1 on both `--paper` and white.

---

### 5. The header cannot reasonably fit at 320px

**Severity: High**

The mobile rule only reduces link font size:

```css
header.site nav a { font-size: 12px; }
```

—`fixtures/site/styles.css:95-100`

The header still contains the wordmark, three navigation links, a menu button, 80px total horizontal padding, 32px outer gaps, and 24px navigation gaps (`styles.css:31-40`). This exceeds a 320px viewport and is likely to cause clipping or horizontal scrolling.

The menu button at `index.html:19` does not hide or operate the navigation, so it consumes space without providing mobile behavior.

**Rule:** WCAG 1.4.10 Reflow requires content to work at 320 CSS pixels without two-dimensional scrolling, except where essential.

**Fix:** Define an actual mobile navigation state. Do not simultaneously show the full navigation and an inert menu button.

---

### 6. The mobile signup form is also likely to overflow

**Severity: High**

`fixtures/site/styles.css:86-87` keeps the form in a single flex row, while `styles.css:43` leaves only 240px of content width at a 320px viewport. The email field and “Create workspace” button are unlikely to shrink into that width cleanly.

No mobile rule stacks or wraps the form.

**Rule:** WCAG 1.4.10 Reflow, measured at a 320 CSS-pixel viewport.

**Fix:** Stack the input and button or allow wrapping at narrow widths; add `min-width: 0` where appropriate.

---

### 7. The email field does not use email-input semantics

**Severity: High**

`fixtures/site/index.html:70` uses `type="text"` for an email address and does not provide `autocomplete="email"`.

Consequences include no built-in email-format validation, a less useful mobile keyboard, and poorer autofill support.

**Rules:**

- WCAG 1.3.5 Identify Input Purpose requires programmatically identifiable common input purposes.
- HTML input semantics define `type="email"` for email addresses.

**Fix:** Use `type="email"` and `autocomplete="email"`. If signup genuinely requires an address, also use `required` and provide accessible validation feedback.

---

### 8. Duplicate `id="cta"` values make the document invalid

**Severity: Medium**

The same ID appears at:

- `fixtures/site/index.html:17`
- `fixtures/site/index.html:26`

IDs must be unique. Duplicate IDs can make DOM queries, fragment references, analytics, and accessibility relationships ambiguous.

**Rule:** HTML’s `id` value must be unique within the document. This is also a robustness issue under WCAG 4.1.1 parsing expectations, even though WCAG 2.2 no longer treats all parser errors as automatic failures.

**Fix:** Remove these IDs if unused or give each element a unique descriptive ID.

---

### 9. Multiple icon buttons have no accessible names

**Severity: High**

The header menu button at `fixtures/site/index.html:19` and all five arrow buttons at lines 45, 49, 53, 57, and 61 contain only unnamed SVGs.

A screen reader will typically announce these simply as “button,” with no purpose. The menu control also lacks `aria-expanded` and `aria-controls`, and there is no script implementing it.

**Rule:** WCAG 4.1.2 Name, Role, Value. If the menu button is functional, its state must also be exposed.

**Fix:** Give functional controls explicit names and states. Remove controls that have no distinct action.

---

### 10. Content is hidden until JavaScript executes

**Severity: Medium**

`fixtures/site/styles.css:92` makes every `.reveal` section transparent by default. JavaScript at `fixtures/site/index.html:80-85` is the only mechanism that reveals it.

If JavaScript fails, `IntersectionObserver` is unavailable, or script execution is blocked, “How it works,” integrations, and signup remain invisible despite being in the DOM.

**Measurement:** Three primary sections—lines 30, 39, and 66—start at `opacity: 0`.

**Fix:** Make content visible by default. Add the hidden animation state only after JavaScript has successfully initialized.

---

### 11. Motion preferences are ignored

**Severity: Medium**

`fixtures/site/styles.css:92-93` applies a 500ms movement and fade to every revealed section, with no `prefers-reduced-motion` override.

**Rule:** WCAG 2.3.3 Animation from Interactions is an AAA criterion, but respecting the operating-system motion preference is established accessibility practice and reduces vestibular discomfort.

**Fix:** Under `@media (prefers-reduced-motion: reduce)`, disable the transform and transition.

---

### 12. “Connects to 12” is unsupported by the visible list

**Severity: Medium**

`fixtures/site/index.html:41` claims twelve supported practice-management systems, but lines 43–62 show only five and provide no “view all” explanation.

This leaves users unable to verify whether their system is among the other seven.

**Rule/measurement:** The page states **12** but visibly identifies **5**.

**Fix:** List all twelve, link to a full compatibility list, or clarify that the five shown are examples.

---

### 13. Logo alternative text repeats adjacent text

**Severity: Low**

For example, `fixtures/site/index.html:44` contains an image with `alt="ezyVet logo"` immediately followed by the visible text “ezyVet.” The same duplication occurs at lines 48, 52, 56, and 60.

Screen-reader output can become “ezyVet logo, ezyVet.”

**Rule:** Under WCAG 1.1.1 Non-text Content, decorative or redundant images should generally use empty alternative text.

**Fix:** Use `alt=""` for these logos because the adjacent text already identifies each integration.

---

### 14. No skip link is provided

**Severity: Low**

The document starts with several header controls before the main content (`fixtures/site/index.html:12-22`) but has no mechanism to skip directly to `<main>`.

**Rule:** WCAG 2.4.1 Bypass Blocks requires a way to bypass repeated content blocks. A skip link is the standard implementation.

**Fix:** Add a keyboard-visible “Skip to main content” link targeting an ID on `<main>`.

---

### 15. Mobile primary buttons become unnecessarily small

**Severity: Low**

At `fixtures/site/styles.css:98`, all `.btn` elements shrink to 13px text with only 4px vertical padding. The resulting height is roughly 31px.

This passes WCAG 2.5.8’s 24×24px AA minimum but falls below the commonly recommended **44×44px** target and WCAG 2.5.5’s AAA target size.

**Fix:** Preserve a minimum control height around 44px on touch layouts rather than shrinking the primary actions.

---

### 16. Four externally hosted font families add avoidable dependency and weight

**Severity: Low**

`fixtures/site/index.html:7-8` requests Inter, Playfair Display, Roboto Mono, and Lobster from Google Fonts. Three families are used for relatively small amounts of display text.

**Measurement:** Four font families are requested through a third-party stylesheet before local CSS. No `crossorigin` is set on the Google Fonts preconnect.

**Fix:** Limit the number of families/weights and add the appropriate preconnect configuration, or self-host if privacy and predictable loading are priorities.

## What is working

- The page has a valid language declaration and viewport metadata: `index.html:2-5`.
- Heading order is coherent: one `h1`, followed by section `h2`s and card `h3`s.
- Major content is contained in `<main>` and primary navigation is labelled.
- The hero image has explicit dimensions, reducing layout shift: `index.html:27`.
- Desktop line length is constrained to 62 characters: `styles.css:25`.
- The three-column feature grid collapses to one column on mobile: `styles.css:95-97`.
- Main text and accent colors themselves have adequate contrast; the principal failure is the muted color token.

## Recommended implementation order

1. **Keyboard and controls:** focus styles, integration-row semantics, button names.
2. **Form accessibility:** label, `type="email"`, autocomplete, validation.
3. **Color contrast:** replace the muted text token.
4. **Responsive layout:** header/navigation and stacked signup form at 320px.
5. **Robustness:** unique IDs and visible-by-default reveal behavior.
6. **Content and polish:** integration-count explanation, reduced motion, redundant logo alt text, skip link, touch sizing, font loading.
